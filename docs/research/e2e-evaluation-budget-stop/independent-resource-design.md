## Diagnosed causes, with limits of evidence

`pipeline.run` processes 36 protected cells serially; `protected._evaluate_cell_body` processes eight methods serially inside each cell. A cell regenerates all histories once for the common scoring policy and once per method: nine generation passes. Every protected factory history calls `live.check()`, `freeze.read()`, grant verification, then `generate_episode`; the generator verifies the grant/source again. `FrozenStudyRef.read` recomputes the whole executable identity each time. The generator does bounded support-query rejection and exact target arithmetic on every pass. `study._evaluate` streams each singleton history, batches up to 64 read requests into a fresh subprocess, and scores them. Chunk size 128 is not parallel execution.

A major directly measured overhead is `resources.LiveStageGuard.check`: it synchronously calls `_record`, whose default `pipeline.observe_resources` invokes vm_stat, sysctl and ps and recursively scans output files. It runs in addition to a 0.1 s background sampler and an outer StageLedger sampler. For 16-history pilots the inner guard records 283–286 observations on short cells and 594–601 on long cells. Its accumulated observer time is 10.46–10.60 s on roughly 18.5 s short cells and 25.69–26.28 s on roughly 68.6 s long cells. These times overlap background/scientific work and must not simply be subtracted from elapsed time to claim a speedup. The code nonetheless makes roughly 144 synchronous history checks per pilot and 2,304 per 256-history cell, independent of background sampling.

Actual scientific work is also material. On the 2048-event piecewise pilot, buckets streaming takes 12.69 s and Laguerre reference streaming 11.24 s for 16 histories. Other methods' stream times range from 1.10 to 3.14 s. Read worker time is approximately 0.65–1.00 s per method/batch, and scoring roughly 0.02–0.04 s. On the short pilot, each method has approximately 0.65 s cold worker cost. The unallocated portion of per-method elapsed time includes repeated generation, hashing and admission; it has not been separately profiled. These are source-supported causes and observed cost components, not a speculative assertion that CPU cores alone fix the problem.

## Follow-up: actual first-cell time, limiter design, and the safer fallback

Root reports the first 256-history 128-event confirmation cell took 156.8 s (resource-only timing). This is substantially below the 296 s naive pilot scaling, consistent with fixed overhead and batching. It does not establish a long-cell fit under 600 s. A purely illustrative affine history model fitting 18.5 s at H=16 and 156.8 s at H=256 has a 9.28 s fixed cost and 0.576 s/history short-cell cost. Assuming that same fixed cost across lengths projects approximately 157/315/958 s for 256-history short/medium/long cells, or 3.18 h for both panels. That cross-length fixed-cost assumption is unvalidated; preserve the 4.11 h linear planning point and headroom rather than making a new completion promise from a short cell.

A bounded rate limiter in `LiveStageGuard.check` is a smaller and more defensible optimization than multiprocessing:

- Every call checks monotonic wall expiry and a latched violation immediately, regardless of sampling cadence.
- Entry and exit force a full observation. One synchronized sampler performs at most one expensive observation at a time; background sampling continues while numerical work is busy. A history check reuses a recent successful sample instead of launching the same vm_stat/sysctl/ps/recursive-stat sequence again.
- Set an explicit finite maximum observation age, for example 0.25 s for a 0.1 s interval with measured 0.035–0.044 s observer durations. If no recent completed sample exists, synchronously refresh or fail closed; never keep returning success on stale data while the background observer hangs. A failed/hung observer must be bounded by the independent owner witness. Use separate synchronization for sample publication and the observation operation to avoid deadlocks.
- Continue comparing the same whole-tree RSS and disk measurements against the same caps. This is sampled enforcement, not proof that no transient spike can ever exceed the cap. Document the maximum observation age and detection latency; do not silently change what current RSS means.
- Receipts include forced/background/reused sample counters, maximum successful-sample age and elapsed observation time, and every violation. Preserve no-success-after-violation semantics and no deadline reset on resume.
- Source-only/public deterministic tests must cover deadline expiry while cached, a stale or failing observer, concurrent caller/background sample races, entry/exit force, RSS/disk violation and teardown. No protected score comparison is needed or permitted for choosing the sampling rate.

Changing resources.py leaves E3 and transfer byte identities intact but changes the all-executable freeze, so it is legal only in the new dated source revision/run. Forty percent wall reduction is not established; the observer time totals overlap the background work and remain only a reason to test the optimization publicly. The new 1,800 s local / 8 h whole-run budget should make completion feasible even if this optimization saves little.

### Revised lowest-risk decision after measuring the public fallback

The original preference above is to **reuse** all public work when import is independently demonstrated correct. However, the strictly simplest implementation and lowest provenance risk is actually a new complete run with deterministic public recomputation, because the existing source already supports a single-root end-to-end ledger and portable report. The completed public stages cost approximately 4,032 s (67.2 min): K16 development 1,686.19 s, K12 development 1,513.46 s, timing 392.45 s, transfer fit 285.79 s, stress 133.91 s, with the remaining preflight/probes/freeze about 20 s. This is a measured fallback cost, not an unbounded rerun proposal.

Thus: freeze the auditable import design first and accept it only after source/reference/relocation/tamper gates pass without private access. If those gates require invasive surgery or delay comparable to the known 67-minute public recomputation, prefer a new complete run under an explicit prospective amendment, with the small guard optimization optional. Preserve all old 116 fits and costs unchanged as historical evidence. Require deterministic recomputed public selections/checkpoint content to match the old commitments wherever their format is path-independent; compare canonical scientific content separately for path-bound manifests. Any mismatch blocks new private execution rather than permitting model choice. This fallback spends compute but avoids weakening any accepted source, transfer, stage-ledger or report-path validator. User preference for completion and no explicit time budget makes that trade reasonable. It should be stated openly rather than described as reuse.

Implementation for the simpler fallback can be limited to the dated amendment/configuration path in `pipeline.py` (new resource ceilings and fresh full-ID prefix), optional `resources.py` limiter, CLI configuration admission, and narrow tests. E1/E3/transfer/inference stay byte-identical; every stage, grant and full freeze is produced normally under the new executable. The old run retains its original source and policy. No cross-root report/import extension is then required. The one-command CLI and artifact-only report already have the correct architecture.
