An implementer must currently choose unbound fields or an unbound config file to call the named API. **Minimal correction:** bind the exact resolved original config or file bytes by `Ref`, prescribe the permitted `eval_histories_per_cell=8` and per-entry length/regime substitutions, and verify the resulting data/seed plus all 96 event/query/oracle hashes against the bound manifest. If a different constructor is intended, specify its complete typed inputs and the exact existing validation path. This does not authorize generating the panel now.

2. **The authority hash preimages are not closed.** Design lines 30–40 introduce `Approval.evidence_sha256` and `Release.payload_sha256`; lines 94–106 introduce a `template_sha256` shared by launch, qualification and binding report, while allowing fresh absolute ROOT/PLAN substitutions and a distinct hash for each literal argv. The documents do not state whether `evidence_sha256` hashes the canonical `Evidence` object, the archive mapping bytes, or another record; nor do they give a byte representation for the symbolic template. “Canonical payload” specifies the excluded field but not its serializer. Existing source has concrete, different-purpose helpers: `validation/kernel_stage_a/authority.py:30–35` hashes sorted compact UTF-8 JSON, and `validation/kernel_stage_a/commands.py:29–30` hashes compact JSON argv. A competent builder must invent the approval check and the equality that lets a static bootstrap qualification carry across new paths/times. **Minimal correction:** define each hash as SHA-256 over named exact bytes (including canonical JSON options and precise excluded fields), define the symbolic template as an exact ordered string array with literal placeholder tokens and ROOT/PLAN substitution rules, and name the existing argv hash convention or replace it explicitly. Require both full Git IDs to remain recorded and require the existing explicit compatibility ruling when they differ; do not equate Git IDs merely because template hashes match.
